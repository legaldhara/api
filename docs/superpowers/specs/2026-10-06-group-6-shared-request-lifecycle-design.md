# Group 6: Shared Request Lifecycle Design

## Scope

Group 6 replaces the separate application and certificate workflows with one server-enforced lifecycle. It resolves:

- BUG-023: status transitions are not enforced
- BUG-024: document requests are stored as transient update flags
- BUG-025: clients can forge timeline event types and history can be edited
- BUG-026: certificate replies require attachments and users cannot reply during review
- BUG-027: attachments are not tied to a specific case or requirement
- BUG-030: customers receive no notification when an administrator acts

The production workflow database is empty, so the migration does not need a legacy request backfill. Existing application and certificate endpoints remain available during the frontend rollout.

Group 5 retains ownership of plan benefits, plan expiry, invoices, GST, service-fee presentation, and government-fee accounting. Group 4 remains the authority for Razorpay settlement and refunds.

## Goals

1. Give applications and certificate requests one lifecycle, timeline format, requirement model, and authorization policy.
2. Make the server the only authority for status transitions and event types.
3. Keep timeline history append-only.
4. Track document and payment requirements independently so both may remain open at the same time.
5. Let customers send text replies in every non-terminal state.
6. Notify customers through in-app notifications and email when an administrator takes an action that affects them.
7. Keep existing application and certificate domain fields without merging them into one oversized table.

## Non-Goals

- Browser push notifications
- SMS lifecycle notifications
- Reopening rejected or closed requests
- Migrating legacy request records
- Replacing the application and certificate creation forms
- Redesigning website or admin layouts

## Architecture

`RequestCase` owns the shared workflow. `Application` and `CertificateRequest` keep request-specific fields and each reference exactly one case. Controllers load the domain record, then call a shared lifecycle service. Controllers do not write lifecycle status, timeline events, or requirements directly.

The lifecycle service owns:

- transition authorization
- transition guards
- requirement creation and fulfilment
- append-only events
- notification records
- transactional outbox entries for email delivery
- the `availableActions` returned to clients

Payment settlement calls the same lifecycle service through a payment adapter. Upload flows attach only assets owned by the case owner and explicitly selected for a requirement or event.

## Data Model

### RequestCase

`RequestCase` stores the shared state:

- UUID primary key
- `type`: `APPLICATION` or `CERTIFICATE`
- `ownerId`
- `status`: shared `RequestCaseStatus`
- optional one-to-one `applicationId`
- optional one-to-one `certificateRequestId`
- `version` integer for optimistic concurrency
- `submittedAt`, `approvedAt`, `rejectedAt`, `completedAt`, and `closedAt`
- `createdAt` and `updatedAt`

Database constraints enforce exactly one domain relation and require that relation to match `type`. Domain deletion uses soft deletion and does not cascade into case events, requirements, payment records, or notification audit records.

### RequestCaseStatus

The shared statuses are:

- `SUBMITTED`
- `UNDER_REVIEW`
- `ACTION_REQUIRED`
- `APPROVED`
- `REJECTED`
- `COMPLETED`
- `CLOSED`

`REJECTED` and `CLOSED` are terminal. `COMPLETED` accepts only the transition to `CLOSED`.

### CaseEvent

`CaseEvent` is the immutable timeline:

- UUID primary key
- `caseId`
- `actorId`, nullable only for system events
- `actorRoleSnapshot`
- server-selected `type`
- optional bounded `message`
- `previousStatus` and `newStatus`
- immutable JSON metadata generated by the server
- optional `requirementId`, `paymentChargeId`, or deliverable asset relation
- unique idempotency key where the action can be retried
- `createdAt`

Clients cannot submit an event type, actor identity, status snapshot, payment result, or arbitrary metadata. The API has no update or delete operation for events.

Initial event types are:

- `CASE_SUBMITTED`
- `REVIEW_STARTED`
- `USER_MESSAGE`
- `ADMIN_MESSAGE`
- `DOCUMENTS_REQUESTED`
- `DOCUMENTS_SUBMITTED`
- `PAYMENT_REQUESTED`
- `PAYMENT_CONFIRMED`
- `PAYMENT_FAILED`
- `REQUIREMENT_CANCELLED`
- `CASE_APPROVED`
- `CASE_REJECTED`
- `DELIVERABLE_ATTACHED`
- `CASE_COMPLETED`
- `CASE_CLOSED`

### CaseRequirement

`CaseRequirement` tracks work the customer must complete:

- UUID primary key
- `caseId`
- `type`: `DOCUMENT` or `PAYMENT`
- `status`: `OPEN`, `FULFILLED`, or `CANCELLED`
- administrator who created it
- bounded title and instructions
- optional due date
- optional fulfilled/cancelled actor and timestamp
- optional `paymentChargeId` for payment requirements
- timestamps

A document requirement has one or more requested document labels and receives authorized asset links through a join table. A payment requirement references one server-created `PaymentCharge`. Clients cannot submit an amount or mark a requirement fulfilled.

An administrator may create several document requirements. A case may have only one open payment requirement because Group 4 permits one open payable obligation for a target at a time.

### CaseAsset

`CaseAsset` links an owned uploaded asset to:

- the case
- an optional document requirement
- the event that attached it
- its purpose: `CUSTOMER_DOCUMENT` or `FINAL_DELIVERABLE`

The lifecycle service verifies asset ownership, `TEMPORARY` state, allowed content type, and case ownership before attaching it. One asset cannot be attached to unrelated cases.

### NotificationOutbox

The transaction that changes a case also creates:

- one in-app `Notification`
- one `NotificationOutbox` email job when the event requires customer attention

The outbox stores a template key, recipient user ID, case ID, event ID, delivery state, attempt count, and timestamps. A unique key on event, recipient, channel, and template prevents duplicate emails. A bounded worker sends email after commit and records `SENT` or `FAILED`. Email failure does not roll back the case transaction.

## Transition Rules

| Current status | Action | Actor | Next status | Guards |
|---|---|---|---|---|
| `SUBMITTED` | Start review | Admin or co-admin | `UNDER_REVIEW` | None |
| `SUBMITTED` | Reject | Admin or co-admin | `REJECTED` | Reason required |
| `UNDER_REVIEW` | Request documents | Admin or co-admin | `ACTION_REQUIRED` | Document requirement created |
| `UNDER_REVIEW` | Request payment | Admin or co-admin | `ACTION_REQUIRED` | Server-created charge and payment requirement |
| `UNDER_REVIEW` | Approve | Admin or co-admin | `APPROVED` | No open requirements |
| `UNDER_REVIEW` | Reject | Admin or co-admin | `REJECTED` | Reason required |
| `ACTION_REQUIRED` | Requirement fulfilled | System | `UNDER_REVIEW` | All open requirements fulfilled or cancelled |
| `ACTION_REQUIRED` | Add another requirement | Admin or co-admin | `ACTION_REQUIRED` | Requirement rules pass |
| `ACTION_REQUIRED` | Reject | Admin or co-admin | `REJECTED` | Reason required; open requirements cancelled |
| `APPROVED` | Attach deliverable | Admin or co-admin | `APPROVED` | Owned authorized asset |
| `APPROVED` | Complete | Admin or co-admin | `COMPLETED` | Final deliverable or structured completion record exists; no open requirements |
| `COMPLETED` | Close | Admin | `CLOSED` | Completion event exists |

Users may add `USER_MESSAGE` events in `SUBMITTED`, `UNDER_REVIEW`, `ACTION_REQUIRED`, and `APPROVED`. Administrators may add `ADMIN_MESSAGE` events in every non-terminal state. Messages do not change status.

The service rejects all unlisted transitions with `409 Conflict`. Authorization failures return `404` for customer ownership checks and `403` for authenticated administrators without permission. Validation failures return `400`.

## Requirement Behaviour

### Document Requirements

An administrator supplies a title, instructions, and a bounded list of document labels. The service creates the requirement and a `DOCUMENTS_REQUESTED` event in one transaction.

The customer may reply with text before uploading files. Submitting documents validates each asset, attaches it to the requirement, and creates `DOCUMENTS_SUBMITTED`. The requirement becomes `FULFILLED` only when all required document labels have an attached asset. An administrator may cancel an obsolete requirement with a reason.

### Payment Requirements

An administrator selects the server-supported payment category and purpose. The server validates the amount, creates the `PaymentCharge`, requirement, and `PAYMENT_REQUESTED` event in one transaction.

Only Group 4 settlement may fulfil the requirement. A verified paid charge creates `PAYMENT_CONFIRMED` once. Failed attempts leave the requirement open and create at most one event per meaningful attempt transition. Refunds add an audit event but do not silently reverse legal work or reopen a closed case.

### Returning to Review

After any requirement is fulfilled or cancelled, the service checks all requirements. If none remain open, it moves `ACTION_REQUIRED` to `UNDER_REVIEW` and appends a system event in the same transaction.

## Completion Rules

Both request types require one of these completion records:

- an authorized final deliverable asset, or
- a structured completion record for a service that produces no file

The structured record contains a bounded summary and completion reference. Administrators cannot complete a case with open requirements, an unpaid payment requirement, or no completion record. Certificate requests require a final deliverable asset.

## Service Interface

The lifecycle module exposes commands rather than unrestricted record updates:

- `createCase`
- `startReview`
- `postMessage`
- `requestDocuments`
- `submitDocuments`
- `requestPayment`
- `recordPaymentSettlement`
- `cancelRequirement`
- `approveCase`
- `rejectCase`
- `attachDeliverable`
- `completeCase`
- `closeCase`

Each command accepts the authenticated actor and a strict Zod input. The service loads the case, checks its version, validates the transition, and writes the status, event, requirements, notifications, and outbox records in one Prisma transaction.

Commands use an idempotency key for retryable mutations. A repeated command returns the first result without adding another event, requirement, charge, or notification.

## Read Contract

Application and certificate detail endpoints return a common `lifecycle` object:

```json
{
  "case": {
    "id": "uuid",
    "type": "APPLICATION",
    "status": "ACTION_REQUIRED",
    "version": 3
  },
  "timeline": [],
  "requirements": [],
  "availableActions": []
}
```

The server calculates `availableActions` from actor role, status, open requirements, payment state, and deliverables. Website and admin clients render only these actions. The server still validates every command because client visibility is not authorization.

Customer responses include safe timeline metadata and owned assets. Administrator responses include operational details but omit provider secrets and unrestricted audit payloads.

## API Compatibility

Existing application and certificate creation, list, and detail routes remain during rollout. Their response gains the shared `lifecycle` object.

Existing generic update routes stop accepting status, event type, charge, pending flags, actor identity, or arbitrary metadata. They accept a text message only and delegate to `postMessage`.

New command endpoints use the case ID:

- `POST /api/v1/cases/:caseId/review`
- `POST /api/v1/cases/:caseId/messages`
- `POST /api/v1/cases/:caseId/requirements/documents`
- `POST /api/v1/cases/:caseId/requirements/:requirementId/documents`
- `POST /api/v1/cases/:caseId/requirements/payment`
- `POST /api/v1/cases/:caseId/requirements/:requirementId/cancel`
- `POST /api/v1/cases/:caseId/approve`
- `POST /api/v1/cases/:caseId/reject`
- `POST /api/v1/cases/:caseId/deliverables`
- `POST /api/v1/cases/:caseId/complete`
- `POST /api/v1/cases/:caseId/close`

Administrator mutations require authentication, `ADMIN` or `COADMIN`, and current MFA. Closing a case requires `ADMIN`. Customer mutations require ownership.

## Notifications

The service notifies the customer for:

- review started
- administrator message
- documents requested
- payment requested
- case approved
- case rejected
- deliverable attached
- case completed
- case closed

In-app notifications link to the exact application or certificate detail view. Email templates contain safe request references and action links. They do not contain private document URLs, payment provider payloads, or secrets.

Customer messages and submissions continue to notify administrators through authenticated admin channels. Notification delivery uses the event idempotency key to prevent duplicates.

## Website Changes

The website reads the shared lifecycle object for both request types. It renders:

- shared status labels and timeline entries
- separate open document and payment requirement cards
- text reply controls in every non-terminal customer state
- upload controls only for open document requirements
- Razorpay checkout only for an open payment requirement
- final deliverables only to the case owner

Existing page layout and visual design remain unchanged during Group 6.

## Admin Changes

The admin panel reads `availableActions` and calls command endpoints. It no longer sends arbitrary status strings, update event types, payment results, pending flags, or timeline metadata.

The detail views show open requirements separately from timeline history. The admin may request documents, request payment, message the customer, approve, reject, attach a deliverable, complete, or close only when the server returns that action.

## Concurrency and Integrity

`RequestCase.version` increments on every lifecycle mutation. Commands update the expected version and return `409` when another action wins the race. The client refreshes the case after a conflict.

Unique constraints cover event idempotency keys, notification delivery keys, one case per domain record, and one payment charge per payment requirement. Database transactions include the case change and all durable side effects.

No controller edits earlier events. No delete route removes case events, requirements, payment records, or notification audit records.

## Migration and Rollout

1. Add lifecycle enums, tables, constraints, and indexes in one Prisma migration.
2. Update application and certificate creation to create `RequestCase` and `CASE_SUBMITTED` atomically.
3. Add the lifecycle service and command endpoints behind focused tests.
4. Adapt Group 4 payment settlement to fulfil payment requirements.
5. Return the shared read contract from existing detail endpoints.
6. Update the admin panel to use server-provided actions.
7. Update the website timeline, requirements, replies, uploads, and payments.
8. Remove old pending flags, status writes, and duplicate update logic after both clients use the shared contract.
9. Run local integration and end-to-end tests.
10. Deploy API first, then admin, then website.

The first API deployment keeps existing read routes compatible. Production uses an empty workflow database, so no backfill runs. The legacy-column cleanup is destructive and requires a maintenance window plus a database backup. If validation fails before traffic resumes, restore that backup and the previous API and frontend images together. After traffic resumes on the new schema, roll forward with a corrected Group 6 API image rather than starting the pre-Group 6 API against the cleaned schema.

## Testing

### Lifecycle Unit Tests

- every allowed transition
- every forbidden transition
- role restrictions
- terminal-state protection
- message actions without status changes
- completion guards
- optimistic concurrency conflicts
- idempotent command retries

### Requirement Tests

- document and payment requirements open together
- partial document submission leaves the requirement open
- text replies remain available while requirements are open
- unauthorized or unrelated assets are rejected
- payment fulfilment requires a paid linked charge
- failed payment attempts leave the requirement open
- fulfilling the final requirement returns the case to review

### Audit and Notification Tests

- clients cannot choose event types or actor identities
- existing events cannot be edited or deleted
- one action creates one event and one notification set
- email retry does not duplicate in-app notifications
- sensitive URLs and provider payloads stay out of notifications

### Endpoint Integration Tests

Run the same lifecycle contract suite against application and certificate cases. Test customer ownership, administrator MFA, strict request schemas, response safety, conflict responses, and backward-compatible reads.

### Frontend Tests

- admin renders only `availableActions`
- website renders simultaneous requirements
- customer may message during `ACTION_REQUIRED`
- upload and payment controls target the correct requirement
- terminal cases expose no mutation controls

## Acceptance Criteria

Group 6 is complete when:

- applications and certificates use `RequestCase` as the only lifecycle authority
- all mutations pass through strict command schemas and the shared service
- the database stores append-only events and independent requirements
- payment and document fulfilment use trusted server evidence
- customers can reply in every non-terminal state
- admin actions create deduplicated in-app and email notifications
- both frontends consume the shared read contract
- old pending flags and direct status writes are removed
- focused and full API, website, and admin tests pass
- local end-to-end tests cover the complete application and certificate lifecycle
